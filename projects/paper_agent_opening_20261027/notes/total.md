# 01_cover
各位老师好，我的开题题目是《基于多智能体协同的科研文献智能综述生成系统》。这个项目想解决的不是“让模型更快写出一篇文章”，而是让综述里的每一个关键结论都能回到原文证据。接下来我会用大约十分钟，说明问题、方案、系统设计和评测计划。

---

# 02_background
科研文献数量快速增长，单靠个人持续跟踪已经越来越困难。真正的压力来自三处：检索分散、全文与元数据质量不一、以及引用难以核验。研究者需要的是一张可核查的领域地图，包括方法分类、代表工作、实验条件和演进脉络。因此，本项目的核心判断是：问题的核心是证据链，不是生成速度。

---

# 03_core_idea
传统的单次提示词生成，往往只给出“主题、模型、草稿”这样一条不透明的链路，结论从哪来、引用了哪一段都很难回查。项目把它改造成六段式工作流：规划、检索、分析、对比、写作和校验。每一步都有输入、产物、证据和失败处理，所以我把目标概括为：综述等于任务图乘以证据链再乘以验证。

---

# 04_gap
现有研究可以分成三条线。检索增强生成能引入外部证据，但引用常常停留在段落或文献级；多智能体能分工协作，但自由对话容易造成上下文膨胀和错误级联；自动综述已经有端到端探索，但跨领域评测、冲突处理和工程闭环仍然不足。三条线共同指向同一个切口：细粒度证据定位、结构化任务融合，以及可复现的系统评测。

---

# 05_solution
针对这个缺口，总体方案分为三层。底层用混合 RAG 负责证据，中层用 CrewAI 负责智能体协作，上层用 Web 应用把整个流程封装成可操作界面，并由 LLM 网关、数据库、任务队列和对象存储提供支撑。右侧三条设计原则分别是结构化产物、证据优先和失败可恢复。最终目标是从主题输入到报告导出，每一个阶段都有状态、产物和证据可查。

---

# 06_agents
系统设置六类角色：协调、检索、分析、对比、撰写和引用校验。协调器把主题拆成有依赖的任务图，各节点之间传递 Plan、Retrieval、Analysis、Comparison、Draft 和 Verification 等类型化产物。任务失败时会进入 schema 校验、重试、检查点和人工复核的恢复路径，而不是静默跳过。这样，多智能体协作就从自由对话变成了可检查的工程执行。

---

# 07_rag
RAG 流水线从论文接入开始，经过章节切分、混合召回和重排序，最终形成带 evidenceId 的证据卡片。写作时，关键声明只能引用证据卡片中存在的 ID；例如“方法 A 在数据集 D 上优于 B”，必须绑定原文片段、章节和页码或表格位置。引用校验会检查支持度，达到阈值才自动通过，否则进入人工复核或定向改写。

---

# 08_fusion
结果融合包括归一化、去重、按方法和任务聚类、冲突检测和证据约束写作。遇到不同论文结论冲突时，系统不会强行投票，而是保留双方的实验设置、证据和分歧，交给读者或评审判断。证据质量分由相关性、可信度、可验证性和时效性组成；支持度高于零点七五自动通过，零点五到零点七五进入人工复核，低于零点五拒绝进入正文。

---

# 09_system
工程上，系统分为表现层、应用与编排层、智能体与证据层、数据与存储层。前端有主题输入、任务进度、报告工作区和证据面板四个视图，后端通过 FastAPI、SSE、Celery 和 Redis 管理任务与事件，PostgreSQL、pgvector 和对象存储负责持久化。这样的分层让项目不只是一个演示脚本，而是一个可操作、可恢复、可扩展的软件原型。

---

# 10_requirements
需求已经收敛为十二项功能需求和八项非功能指标。主流程必须支持主题输入、检索、去重、切分、混合检索、分析、对比、结构化写作和引用校验；增强项包括证据查看、报告编辑、多格式导出和任务监控。验收上先保证证据绑定百分之一百、引用精度目标不低于百分之八十五、专家评分目标不低于四分，所有目标值都以最终实验为准。

---

# 11_evaluation
评测选择三个计算机子方向：检索增强生成、LLM 多智能体系统和软件漏洞检测。每个方向准备三个主题，与 Direct LLM、单智能体 RAG、无 RAG 多智能体和本系统四类基线比较。自动指标看引用精度、覆盖率、定位准确率、检索质量、时延和成本；人工评测由三名评分者盲评，并报告 Krippendorff's alpha，目标不低于零点七。我们关心的不是文本像不像，而是有没有证据。

---

# 12_roadmap
项目按二十四星期推进，分成四个阶段。前两星期完成调研和需求冻结；第三到第八星期完成架构、数据接入和 RAG；第九到第十五星期完成智能体编排与 Web 原型；第十六到第二十四星期完成三领域评测、稳定性优化、技术报告和答辩。每个阶段都要有可运行增量，优先保证证据链、任务恢复和可复现实验。

---

# 13_outcomes
预期交付四类成果：可运行的系统、可评测的证据包、可交接的文档，以及可判断的演示材料。系统包括 Web 原型、接口、RAG 流水线和部署说明；评测包包括三领域主题、引用核验样本、自动指标和人工评分脚本。目标值包括证据绑定百分之一百、引用精度不低于百分之八十五、覆盖率不低于百分之八十、专家评分不低于四分，但最终以实测结果为准，不选择性展示样例。

---

# 14_conclusion
最后用三句话总结：任务图管理复杂度，混合 RAG 管理证据，三领域评测验证可行性。这个项目的价值不是替代研究者，而是把证据链变成可检查的工作流，降低综述整理成本并提高引用可追溯性。请各位老师指正研究边界、评测设计和实施风险，下一步我将完成需求冻结，搭建 RAG 基线，并迭代多智能体任务图。谢谢。

---

# 15_uml_use_case
附录的用例图补充系统的边界和参与者。研究者发起提交主题、生成综述、查看证据和编辑导出；管理员负责配置数据源与模型，并监控任务。生成综述必须包含检索并规范化文献，以及校验声明与引用，这两个行为在图中用 include 关系表示。学术数据库作为外部参与者，与检索用例相连。

---

# 16_uml_class
这张类图把证据链落到领域对象。论文由多个证据片段组成，证据可以支撑声明，声明绑定引用，引用再指回证据；报告草稿包含声明，综述项目包含报告版本。连线上标出的多重性说明了一个项目可以有多份草稿、一篇论文可以有多条证据，而一条声明通常需要至少一条引用。

---

# 17_uml_sequence
顺序图展示从主题输入到引用校验的时间顺序。研究者通过 Web UI 创建任务，编排器调用检索和 RAG，随后撰写初稿，并把声明交给校验器。校验不通过时进入 alt 分支，系统补充检索或定向改写，再返回校验；通过后保存报告并通过 SSE 返回完成事件。这样，主流程、返回消息和失败回退都能在同一张图上读出来。
